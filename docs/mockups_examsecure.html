Flux techniques clés (visualisés dans les écrans)

Django REST API = autorité finale. Flutter n'est jamais la source de vérité pour un paiement, un accès ou un rôle.

Flux d'achat KkiaPay

Étudiant choisit une épreuve
↓
Initiation KkiaPay (POST /payments/initiate)
↓
Paiement Mobile Money / CB → référence
↓
Flutter envoie la référence (POST /payments/verify)
↓
Django vérifie auprès de KkiaPay (montant, devise, épreuve, utilisateur)
↓
Transaction SUCCESS + idempotence (aucun doublon)
↓
Achat créé → accès autorisé + notification

Téléchargement sécurisé

Achat validé (1 appareil, 1 téléchargement)
↓
Django génère un DownloadToken temporaire (hashé, expirable, révocable)
↓
Téléchargement contrôlé (auth + achat + appareil + token)
↓
PDF jamais exposé publiquement
↓
Chiffrement local AES (clé en Keystore / Keychain)
↓
Stockage privé + lecteur intégré hors ligne

Déblocage d'appareil

Changement de téléphone / perte / réinstallation
↓
Étudiant : demande + motif (POST /unlock-requests)
↓
Admin : analyse achat, appareil, historique, motif
↓
Approuver / Refuser + réponse à l'étudiant
↓
Notification envoyée (approuvée / refusée)
↓
Si APPROVED : nouvel accès créé explicitement + audit
